Cloud Deployment · Amazon ECS Fargate

From a laptop command to a public, self-healing address

A containerized FastAPI service — the pump health predictor — already runs anywhere Docker is installed. This piece walks through what changes when that same image moves onto AWS: a machine that never sleeps, a network that lets the right traffic in, an address that never changes, and a watcher that replaces the container the moment it dies.

Starting point

What a laptop cannot give a service

The image pump-health:0.1.0 is public on Docker Hub, built for linux/amd64, with uvicorn listening on port 8000. Anyone with Docker can pull and run it — but only for as long as somebody's machine is awake and reachable. Serving real traffic requires four things a laptop structurally cannot provide, and AWS answers each one with a distinct service.

A machine that stays on

Someone else's computer, running continuously, that doesn't go to sleep when the lid closes.

answered by Fargate

A controlled way in

A network that lets requests reach the service, and only the requests that should be allowed to.

answered by VPC + security groups

An address that doesn't change

Containers come and go, each with a new IP. Callers need one name that always resolves.

answered by Load balancer

Something watching

When a container crashes at 3am, something has to notice and start a replacement without being asked.

answered by ECS service
01 · Foundations

The cloud, AWS, regions and zones

The cloud is, at bottom, other people's computers rented by the second. Instead of buying and maintaining a server, compute, storage and networking are rented from a provider that runs large data centres, and billing stops the moment the resources are released. AWS is one of the three largest such providers, alongside Microsoft Azure and Google Cloud, offering more than two hundred services — this deployment only needs about seven of them.

ServiceWhat it does here
IAMDecides who, and what, is allowed to perform each action
VPCA private network inside AWS, built just for this service
ECSRuns containers and keeps the right number of them running
FargateThe underlying machines ECS runs tasks on, fully managed by AWS
Elastic Load BalancingProvides the fixed public address in front of the service
CloudWatchCollects the containers' logs and performance metrics
AWS BudgetsSends an email before the bill becomes a surprise

Regions and availability zones

AWS does not run everything in one place. A region is a separate geographic area — Northern Virginia (us-east-1) and Mumbai (ap-south-1) are examples — and almost every resource belongs to exactly one of them. Switch the console to a different region and a resource created elsewhere simply isn't there; it's the most common "where did my resource go" moment for newcomers.

Each region is split into several availability zones (AZs): one or more data centres with independent power and networking, far enough apart that a local outage in one doesn't take down the next. This deployment uses two zones in us-east-1. A load balancer requires at least two, and spreading the service across them means one zone can fail while the service keeps answering.

02 · Access control

Who can do what, and signing in

Nothing happens on AWS until something explicitly allows it. Every action — reading a log, pulling an image — is checked against a permission. IAM (Identity and Access Management) is the service that holds those permissions, and four terms cover almost all of it.

User

A person, or a program acting for one, holding long-lived credentials.

Role

A set of permissions with no password. A person or an AWS service temporarily takes on a role and receives short-lived credentials — ECS takes on a role to pull an image and write logs.

Policy

A JSON document listing which actions are allowed on which resources, attached to a user or a role.

Least privilege

Giving each user or role only what it needs, so leaked credentials cause limited damage.

About the root user

A new AWS account's root user — the sign-up email — can do absolutely everything, including closing the account. It should be used only to set up the account, protected with multi-factor authentication, and then set aside in favour of an everyday identity for day-to-day work.

03 · Budget first

What this costs, before building anything

Most of what gets built is free by itself: the VPC, subnets, route table, internet gateway, security groups, cluster, task definition and IAM role cost nothing. Three things are billed by the hour for as long as they exist.

≈ $0.012 / hr

Application Load Balancer

Base rate plus traffic-based capacity units

≈ $0.023 / hr

$0.0225/hr + $0.008 per LCU‑hr

Public IPv4 addresses

Two for the load balancer, one for the task

≈ $0.015 / hr

$0.005 per address‑hr × 3

Running total

All three together come to roughly 5 US cents an hour in us-east-1. Left running by mistake, the same setup costs about $36 a month. CloudWatch Logs adds $0.50 per GB, but the first 5 GB each month are free, and this service writes only a few kilobytes.

Because nothing on AWS warns about a growing bill on its own, a budget is worth setting before creating anything else — an alert that emails at a chosen spending threshold. A budget is an alarm, not a limiter: AWS keeps resources running after the email sends. The only thing that actually stops the charges is deleting the resources.

04 · Networking

The network the service lives in

Every container, load balancer and server on AWS sits inside a network, and a wrong setting here produces unhelpful symptoms — tasks hang while pulling an image, or the load balancer answers with errors for no visible reason. New accounts come with a ready-made default VPC, but building a dedicated one makes every piece visible and keeps teardown clean.

PieceWhat it does
VPCA private network with its own range of IP addresses; nothing else shares it
SubnetA slice of the VPC's address range, confined to one availability zone
Internet gatewayThe single door between the VPC and the public internet
Route tableRules telling traffic where to go; a subnet whose table points at the gateway is a public subnet
Security groupA firewall on a resource, listing exactly which traffic may reach it

10.0.0.0/16 — CIDR notation for "every address starting with 10.0." — gives 65,536 private addresses that can never collide with a real internet address. This deployment uses two public subnets, one per availability zone, with no NAT gateway, since nothing here needs outbound access from a private subnet.

What actually makes a subnet "public"

A subnet is public purely because of its route table, not its name. 10.0.0.0/16 — the VPC's own range — stays local; 0.0.0.0/0, meaning any address at all, is routed to the internet gateway. A missing route here is the most common ECS networking mistake, and it fails silently: the gateway and subnet both exist, the console looks fine, but tasks can't reach Docker Hub and simply hang while pulling an image, then stop.

Why chain the groups

The load balancer's address can change or multiply. By naming its security group as the source — rather than an address range — the rule for the task stays correct no matter what the load balancer's address is, and every request is forced through it.

05 · Container orchestration

ECS in four words

Running a single VM with Docker installed works until the container crashes, the machine needs a patch, or traffic outgrows it — at which point a person has to notice and fix it by hand. 06 · The fixed address

The load balancer

Every Fargate task gets its own IP, and a replacement task gets a new one — so callers can never be handed a task's own address. An Application Load Balancer (ALB) solves this with one DNS name that never changes, forwarding each request to a healthy task behind it.

Listener

Waits on a port of the load balancer — here, port 80 — and defines what happens to each request that arrives.

Target group

The list of places requests may go. For Fargate, targets are IP addresses, since tasks have no fixed machine; the ECS service adds and removes them automatically.

Health check

GET /health every 10 seconds. Two consecutive passes mark a target Healthy. Three consecutive failures mark it Unhealthy, at which point it stops receiving traffic and ECS replaces it.

These thresholds (2 passes / 3 failures, 10-second interval) are tightened from AWS's defaults of 5 passes at 30-second intervals — the defaults would otherwise make a fresh task wait minutes before serving traffic. This is also why the pump service exposes /health at all: it only returns 200 once the model has finished loading, exactly the moment it's ready to serve.

07 · Putting it together

Deploying the pump service

Every piece above comes together into one architecture. The network holds everything; the load balancer sits across both public subnets; the service keeps one Fargate task running and ships its logs to CloudWatch.

What each creation step actually defines

  • Target group — starts empty; ECS populates it as tasks start
  • Load balancer — takes a few minutes to provision; its DNS name is the one address callers ever need
  • Task execution role — the role ECS takes on to pull the image and ship container output to CloudWatch
  • Task definition — names the image, .25 vCPU / .5 GB, container port 8000, and the execution role; saving it creates a new numbered revision and an auto-created log group
  • Service — desired count of 1 task, a 30-second health-check grace period while the model loads, and a public IP on the task (required here, since the task has no other path to Docker Hub)

Calling it through the load balancer

The same two requests that worked against the container on a laptop now go to the public DNS name instead:

$ curl -s "http://$ALB/health"
{"status":"ok","model_version":"20260924-102606","trained_with_sklearn":"1.9.1","running_sklearn":"1.9.1"}

$ curl -s -X POST "http://$ALB/predict" -d '{...}'
{"failure_probability":0.806,"inspect":true,"threshold":0.3,"model_version":"20260924-102606"}

The reading's failure probability (0.806) clears the 0.3 threshold, so inspect comes back true. The request travelled from the caller to the load balancer on port 80, through the listener and target group, to the task on port 8000, and back — the task's own address never appeared anywhere.

08 · Observability

Watching it run

A service nobody can see into is a service nobody can fix. ECS exposes three views: the container's own logs, the service's events, and its metrics.

Logs

Nearly every log line is uvicorn answering GET /health with 200 OK, arriving from the load balancer's own node addresses — one per zone — rather than from any caller directly, since the load balancer forwards every request on the caller's behalf.

Events — watching the service self-heal

Stopping the only running task, as if the container had crashed, shows exactly what the service is for. Nobody tells it to do anything afterward.

15:17 – 15:18
Steady state

The first task starts, is registered with the target group, and the service reaches a steady state.

15:33
Task stopped on purpose

The running task is deregistered from the target group and its connections drained, so no further requests reach a dying container.

15:33 (same minute)
Replacement starts

The service starts a new task with a new ID and registers it — running again roughly 7 seconds after the stop.

15:34
Steady again

The service is stable once more — about 24 seconds of total disruption from a single-task setup. Two tasks across two zones would have answered throughout with no gap.

Metrics

ECS reports each service's CPU and memory to CloudWatch every minute, as a percentage of what the task definition requested.

09 · Failure modes

What goes wrong

Some failures are loud and explain themselves. Others look perfectly healthy from outside while something underneath is quietly broken. Three deliberately induced failures cover the patterns worth recognising on sight.

Every task has a public IP, since it needs one to reach Docker Hub. Calling that IP directly on port 8000, skipping the load balancer entirely:

$ curl -s -m 5 "http://$TASK_IP:8000/health"
curl gave up after 5 s, exit code 28

No refusal, no response — just a timeout. That's how a security group behaves: the task's group only admits port 8000 from the load balancer's group, so a request arriving straight from the internet is silently dropped. The container was healthy the entire time. Lesson: when a request hangs and times out rather than being refused outright, suspect a security group or a missing route before suspecting the application.

If the health check's path is pointed at an endpoint that doesn't exist, the target group marks the task Unhealthy with a 404 reason, and ECS starts a replacement. But the public address is asked for /health directly while this is happening:

$ curl -s "http://$ALB/health"
the public address still answers /health with HTTP 200

When every target in a group is unhealthy, an Application Load Balancer fails open — it sends traffic anyway, on the theory that a possibly-wrong answer beats no answer at all. A caller notices nothing, even as ECS quietly replaces the same task over and over, since the new task fails the identical check. Lesson: a service that keeps replacing tasks whose own logs look fine means the health-check path should be compared against what the app actually serves.

A separate task definition pointed at pump-health:0.1.O — a capital letter O in place of a zero — run directly, without a service, to isolate the mistake:

CannotPullContainerError
ECS retried 7 times to find mlopsatscaler/pump-health:0.1.O on Docker Hub.
Task stopped ~95 seconds after creation.

This one is loud: the console states the reason in plain text. In a service, the same mistake is worse — it keeps starting new tasks that fail identically, filling the event log with the same message. Lesson: the same error also appears for a private image with no pull credentials, or a subnet with no internet route — read to the end of the message; "not found" points specifically at the name or tag.

Pushing a fix under the same tag

ECS resolves a tag to an exact image digest the moment a task starts; running tasks never look again. A later push of the same tag only takes effect for a new task — for example after a forced new deployment. Using a unique tag per build, and a new task-definition revision to match, keeps what's running unambiguous and makes rollback a single click.

An arm64 image on x86 Fargate

An image built on Apple silicon without --platform linux/amd64 is arm64-only. On x86 Fargate, the task starts and stops immediately with exec format error. Either build for amd64, or choose a Linux/ARM64 task definition — which Fargate also supports, and which costs slightly less.

10 · Cleanup

Tearing it all down

Every hour the load balancer and task exist, they're billed, whether or not anyone calls them. Deletion runs in the reverse order of creation, because AWS refuses to remove anything that something else still depends on.

1

Service

Deleted first, with its running task force-stopped. Once it's gone, the target group has no targets and the load balancer has nothing to answer for.

2

Load balancer → target group

The load balancer goes first, taking its listener with it; the now-unused target group follows.

3

Cluster → task definitions

The cluster label is removed; task definition families are deregistered, then deleted.

4

Log groups

CloudWatch log groups are cheap but never expire on their own, so each one is removed explicitly.

5

VPC

Deleting the VPC takes the internet gateway, route table, both security groups and both subnets with it in one action.

A diagnostic worth remembering

With the service deleted but the load balancer still up, the public address answers 503 Service Temporarily Unavailable — a response from the load balancer itself, not the application. Whenever a load balancer returns 503, the real question is why it has no healthy targets; the answer almost always lives in the ECS service, not the app code. The budget and the task execution role are usually left in place — both are free, and the role is reused by the next deployment.

11 · Context

Where this fits in the lifecycle

An experiment gets tracked, the chosen model is served through FastAPI, the app is packaged into an image and pushed to a registry — and now that image runs on AWS behind a fixed address. Everything here was built by hand in the console, on purpose, so each piece and its connections are visible. A command-line and CI/CD pipeline — pushing to Amazon ECR, registering new task-definition revisions, and updating the service automatically — is the natural next step once the pieces are familiar.

Key takeaways

Summary

Cloud = rented, zoned computers

Almost every resource lives in one region; running across two availability zones survives either one failing.

Nothing is allowed by default

IAM checks every action; roles hand out short-lived permissions, and least privilege limits what leaked credentials can do.

Know the bill before you build

The network and ECS definitions are free; the load balancer, task compute, and public IPs are billed hourly. Only deletion stops the charges.

The network is two chained firewalls

A public subnet is defined by its route table, not its name; the task's security group trusts only the load balancer's group.

ECS keeps a description true

Cluster, task definition, task, service — a service replaces anything that stops and registers it with the load balancer automatically.

A broken health check can hide

An ALB with zero healthy targets still answers traffic — fails open — so debugging starts at service events, not just outside symptoms.
